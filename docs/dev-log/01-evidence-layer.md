용어 미리 보기(처음 나올 때 다시 풀어 씀)
- **tenant**: 고객·조직 단위로 데이터를 분리한 공간.
- **원장(ledger)**: 레코드마다 서명하고 앞 레코드의 해시를 이어 붙여, 중간 변경을 들키게 만든 추가 전용 기록.
- **Merkle 트리 / RFC 6962**: 많은 레코드를 하나의 루트 해시로 요약하고 "이 레코드가 들어 있다"(포함 증명), "옛 로그가 새 로그의 앞부분이다"(일관성 증명)를 짧게 보여 주는 구조. Certificate Transparency 표준.
- **C2SP 체크포인트 / 위트니스**: 로그 크기와 루트를 서명한 짧은 문서(체크포인트)를 독립된 제3자(위트니스)가 일관성을 확인한 뒤 공동서명하는 표준 방식. 운영자가 로그를 되돌리거나 두 갈래로 만들면 위트니스가 거부한다.
- **OTLP / OpenTelemetry**: 애플리케이션 추적(trace) 데이터를 보내는 업계 표준 프로토콜과 계측 도구 모음.
- **OCSF**: 보안 이벤트를 SIEM들이 공통으로 읽도록 정한 스키마.
- **DSSE / in-toto**: 서명할 내용을 봉투에 담는 표준(DSSE)과, "무엇에 대해 무엇을 주장하는가"를 적는 증명 형식(in-toto Statement).
- **4-eyes(두 사람 원칙)**: 한 사람이 만들거나 요청한 것을 다른 사람이 승인해야 효력이 생기는 규칙.

### 2026-09-09 · 첫 구현 공개: 서명 원장 기반 AI 행동 감사 파일럿
- **커밋:** `b24f4d4`..`0b96781` (초기 구현, 아키텍처·개발 문서, PDF 핸드북, 문서 뷰어)
- **무엇이 바뀌었나:** Node.js 24 + SQLite 기반의 vault(서명 원장 저장소)·ingress(수집 게이트웨이)·audit(감사 화면)·worker(분석) 네 프로세스 구조, 한국어 감사 UI, Kubernetes 배포 매니페스트와 부하·분산 시험 Job, 설계 철학·아키텍처·수집 계약 문서가 처음 저장소에 올라갔다. (`b24f4d4` 파일 목록, `docs/architecture-draft.md`, `docs/philosophy.md`)
- **어떤 문제였나:** 업무용 AI 에이전트가 "무엇을 했다"고 스스로 보고한 내용과, 실제 도구 결과·권한·승인이 일치하는지 사람이 확인할 수단이 없었다. 설계 철학 문서는 "볼 수 없는 것은 다스릴 수 없다"를 출발점으로, 관측되지 않은 범위를 숨기지 말 것을 원칙으로 삼았다. (`docs/philosophy.md`)
- **고민한 점:** 자기보고·독립 결과·출처 인증·무결성을 하나의 "성공" 값으로 합치면 기록이 없을 때 통과로 오인된다. 그래서 이들을 서로 다른 필드와 상태로 두고, 기록 부재가 "무사고"로 바뀌지 않게 했다. 서명은 "보관된 바이트가 바뀌지 않았다"는 증거일 뿐 출처 주장이 사실이라는 보장은 아니라고 명시했다. (`docs/philosophy.md`)
- **해결 방법:** 출처별 HMAC 인증으로 tenant·출처를 페이로드가 아니라 자격에서 결정, 이벤트 암호화 저장, Ed25519 서명 원장과 별도 신뢰 키로 검증하는 독립 내보내기, 두 사람 승인이 필요한 룰·예외·파기 계획. (`docs/progress-matrix.md` @ `b24f4d4`)
- **결과:** 09-08 측정 기록 기준 Kubernetes 내부 Service 분산 수집 60/60·감사 60/60(각 Pod 2개), HPA(부하에 따른 자동 확장) replica 2→3→2 동안 성공 접수 515건 보존, 다만 8건 timeout. Linux 독립 컨테이너 전체 회귀 70/70 PASS, Windows는 loopback 오류로 56 PASS/10 FAIL을 따로 기록. (`docs/portfolio.md`, `docs/progress-matrix.md` @ `b24f4d4`)
- **포트폴리오 한 줄:** AI 에이전트의 자기보고·도구 결과·권한을 대조하는 서명 원장 기반 감사 파일럿을 Node.js/SQLite/Kubernetes로 구현하고, 실패한 시험까지 원자료로 남기는 검증 문화를 세웠다.

- **고민한 점:** 변경이 생기면 모든 평가를 재검토로 돌릴지, 연결된 의무만 돌릴지 정해야 했다. 후자를 택해 공급사 문서가 바뀌면 그 문서에 기댄 위험관리 근거만 재검토로 돌린다. 금융 업무라는 이유만으로 고영향 AI로 확정하지 않고, 공급사 근거 재사용은 위험·설명·보호 조치 3종(`KR-34-*`)으로 한정했다. 사람 감독과 문서 보관 의무는 자동 승계하지 않는다. (`docs/finance-evidence-20260922.md`)
- **해결 방법:** 공급 모델·목적이 없거나 다르면 `SUPPLIED_*_UNKNOWN/MISMATCH` 재검토 지점을 남기고 충분 평가를 막는다. 감독 계획만 있고 수행 기록이 없으면 과제를 종결하지 못한다. 평가 당시 문서 해시를 서버가 고정하고, 보고서는 별도로 고정한 공개키로만 검증한다. 실제 자료로 신고한 묶음에는 담당자의 3항목 출처 확인 기록을 요구하되, 확인 후에도 `not_independently_verified`를 유지한다. (`docs/finance-evidence-20260922.md`)
- **결과:** 데모 6/6 시나리오, 확인 항목 87개 통과, 관련 회귀 46/46. 첫 회귀는 52/53이었고 실패 로그를 보존했다. 시험 중 네트워크 호출 0. (`docs/portfolio-governance-demo-20261005.ko.md`)
- **포트폴리오 한 줄:** 공급사 문서·모델 버전·사용 목적이 바뀔 때 영향받는 의무만 재검토로 돌리는 증거 대조 흐름을 구현하고, 6개 시나리오·87개 확인 항목으로 재현 가능하게 검증했다.

## 이 시기에 배운 점

- **자기 제품을 공격자 눈으로 다시 보는 것이 가장 큰 진전을 만들었다.** 09-09 첫 감사(A1–A5)와 10-06 적대적 감사(S1–S12)가 방향을 바꿨다. 이후 라운드마다 재감사를 먼저 하고, PoC를 뒤집어 회귀 시험으로 남기는 습관이 굳었다. 그 결과 7라운드 동안 실패 0을 유지하며 시험이 1,189건에서 1,420건으로 늘었다.
- **서명만으로는 부족하다. 무엇을 누구에게서 지키는지 보증 수준을 이름으로 드러내야 한다.** `database_tamper` → `signing_key_holder` → `vault_host`처럼 검증 결과에 "무엇에 대해 확인됐는지"를 표시하자, 과대 주장을 피하고 다음 단계 과제도 분명해졌다.
- **바퀴를 다시 만들지 않는 것이 차별화에 더 유리했다.** OTLP·C2SP·DSSE·in-toto·OPA·CIBA 같은 표준에 붙이고, 직접 만드는 부분은 실제 상호운용 시험(litewitness, OTel Collector, Go 검증기)으로 보정했다. 그 덕에 "위에 얹는 검증 계층"이라는 포지션이 설득력을 얻었다.
- **경쟁 조사는 주장을 줄이는 도구다.** 비슷한 제품(Traefik Hub, remit, MS AGT, DeepInspect)을 찾은 뒤 차별점을 더 좁고 방어 가능한 범위로 다시 썼다. 데이터에 없는 규제 매핑 주장도 스스로 정정했다.
- **성능은 측정이 먼저이고, 보장은 협상 대상이 아니다.** 프로파일링으로 병목을 찾고, 202=영속·fsync·검증 형식을 유지한 채 처리량을 약 4배로 올렸다. 목표 미달과 CPU 고정의 역효과도 숫자로 공개했다. 측정 방법(부하 생성기 분리)이 결론을 바꿀 수 있다는 것도 배웠다.
- **편의 기능일수록 기본값과 권한 설계가 중요하다.** 로그 로테이션, 승인 대기열, 판정 보내기 모두 기본 꺼짐·미리보기, 4-eyes, fail-closed로 설계했다. 각 선택의 비용(가용성, 운영 부담)은 운영자 안내에 적었다.
- **"모른다"를 상태로 표현하는 것이 감사 제품의 신뢰를 만든다.** `not_replayable`, `no_evidence_in_package`, `not_independently_verified`, "미확인"처럼 확인하지 못한 것을 성공이나 실패로 뭉개지 않았다. 이 원칙은 09-09 설계 철학에서 시작해 끝까지 이어졌다.
