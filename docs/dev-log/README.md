# 개발 기록 (업데이트별)

EvidScope를 만들며 업데이트마다 무엇이 바뀌었는지 남긴 기록입니다. 어떤 문제가 있었고, 어떤 대안을 놓고 고민해 어떻게 풀었는지, 결과가 몇이었는지, 지금 다시 보면 무엇이 걸리는지까지 적었습니다. 읽는 쪽은 셋을 생각했습니다.

- **사람**: 포트폴리오, 개발 과정 글, 면접을 준비할 때 분야별 페이지를 읽습니다.
- **이력서 도구·경력 분석 엔진**: 같은 내용을 [entries.jsonl](entries.jsonl)과 [career-profile.json](career-profile.json)에서 구조화된 데이터로 읽습니다.
- **나중의 나**: [회고 노트](reflection.md)에서 다시 고민할 질문과 다른 선택을 했다면 어땠을지를 보고, 항목마다 있는 "내 메모" 칸에 생각을 적습니다.

이력서·면접용으로 한 파일에 압축한 요약은 [포트폴리오 컨텍스트](../portfolio-context.ko.md)에 있습니다.

- 기준일: 2026-10-18. 항목 73개(증거 계층 21, 에이전트 모니터링 15, 판정 모델 25, UI/UX 12)
- 기록 안의 "오너"는 프로젝트 오너입니다. 설계·구현·적대적 감사는 역할을 나눈 AI 코딩 에이전트와 함께 했고, 항목마다 누가 결정했는지(`decided_by`)를 적었습니다.
- 숫자에는 모두 출처(커밋 `sha7`, 저장소 문서 경로, 저장소 밖 작업 메모)를 붙였습니다. 출처 없이 짐작한 것은 "(추정)"으로 쓰고 항목의 "확인하지 못한 것"에 모았습니다.
- 학습·평가 데이터는 설계로 만든 합성 데이터와 공개 데이터입니다. 사람이 검토한 라벨은 없습니다.

## 항목 하나에 들어 있는 것

분야별 페이지는 항목마다 아래 순서로 보여 줍니다. 괄호 안은 JSON 키입니다.

| 칸 | 키 | 무엇을 적었나 |
|---|---|---|
| 번호와 제목 | `id`, `title`, `title_en` | 바뀌지 않는 번호(EL-07처럼 분야 코드 + 순번)와 한·영 제목 |
| 기간·상태 | `date_start`, `date_end`, `status` | 완료, 진행 중, 예정, 무효화(결과가 뒤집힘), 대체됨(뒤 항목이 바꿈) |
| 요약·배경 | `summary`, `context` | 무엇을 왜 했고 결과가 무엇인지, 그때 프로젝트가 어떤 상태였는지 |
| 계기 | `trigger` | 오너 요청, 오너 피드백, 적대적 감사, QA, 측정 결과, 계획, 사고·실패, 외부 조사 중 하나와 설명, 오너 원문(있을 때만) |
| 문제·제약 | `problem`, `constraints` | 증상과 영향, 당시 걸려 있던 조건(GPU 메모리, 비용, 데이터 경계 등) |
| 검토한 대안 | `options` | 대안마다 장점, 단점, 채택 여부, 이유. 대안이 하나뿐이었으면 그 이유 |
| 결정 | `decision` | 무엇을, 왜, 누가(오너, AI 에이전트, 둘이 함께, 기록 없음) |
| 한 일 | `actions`, `tech`, `skills` | 실제 작업, 쓴 기술, 보여 준 역량(어휘 키) |
| 결과 | `result`, `metrics` | 지표마다 전·후 값, 단위, 측정 범위, 출처 |
| 되돌아보기 | `tradeoffs`, `lessons`, `reflection` | 치른 비용과 남은 한계, 배운 점, 열린 질문, 다른 선택을 했다면, 다시 볼 시점 |
| 옮겨 쓰기 | `resume`, `interview` | 이력서 문장(한·영), 예상 면접 질문과 답의 요지 |
| 근거 | `evidence`, `related`, `uncertain` | 커밋, 문서, 저장소 밖 출처 이름, 관련 항목, 확인하지 못한 것 |
| 내 메모 | `owner_notes` | 오너가 나중에 적는 칸. 처음에는 비어 있음 |

## 이력서 도구·경력 분석 엔진이 읽는 법

- **한 번에 다 읽으려면** [career-profile.json](career-profile.json)을 읽습니다. `schema`는 `evidscope-career-profile/1`이고, `project`(카드), `skills`(역량별 횟수와 근거 항목 id), `tech`, `achievements`(이력서 문장), `metrics`, `decisions`, `lessons`, `open_questions`가 있습니다.
- **항목 단위로 읽으려면** [entries.jsonl](entries.jsonl)을 한 줄씩 읽습니다. 각 줄의 `record` 값이 분야별 페이지 안의 위치입니다.
- **성과로 쓸 수 있는 것만 고르려면** `status`가 `done`, `in_progress`, `superseded`인 항목을 씁니다. `invalidated`(예: 적대적 감사로 뒤집힌 첫 판정 결과)와 `planned`는 성과가 아니라 과정과 교훈으로만 씁니다. `achievements`는 이미 이 규칙으로 걸러져 있습니다.
- **숫자를 옮길 때는** 지표의 `scope`를 함께 옮깁니다. 예를 들어 판정 모델의 99%는 "설계한 위협 유형 안에서 처음 보는 세션"에 대한 값이지 일반 성능이 아닙니다. `uncertain`에 있는 내용은 단정하지 않습니다.
- **기여를 쓸 때는** `decision.decided_by`를 봅니다. `owner`는 오너가 정한 방향·조건, `ai_agent`는 AI 에이전트가 정한 구현 설계, `joint`는 AI가 낸 대안 중 오너가 고른 것입니다.
- 항목 번호는 바뀌지 않습니다. 새 업데이트는 같은 분야 코드의 다음 번호를 받습니다.

## 다시 생각해 보기

[reflection.md](reflection.md)는 항목마다 남긴 열린 질문(`reflection.open_questions`), 다른 선택을 했다면(`reflection.what_if`), 다시 볼 시점(`reflection.revisit_when`)을 분야별로 모은 문서입니다. 질문은 답이 정해진 수사적 질문이 아니라, 지금도 다르게 볼 수 있는 결정만 골랐습니다.

생각이 정리되면 해당 항목의 `owner_notes`에 적고 생성 스크립트를 다시 돌리면, 분야별 페이지와 회고 노트의 "내 메모"에 그대로 나타납니다. 직접 고치기 번거로우면 Claude에게 "EL-07 메모에 이렇게 적어줘"라고 말해도 됩니다.

## 프로젝트 전체에서 굳어진 원칙

- **만점은 먼저 의심한다.** 라운드마다 적대적 재감사를 먼저 했고, 세션 판정의 첫 "1.0"도 누수와 라벨 지름길로 무효화했다. 모든 판정 회차에 모델 없는 단순 기준선과 누수 검사를 넣었다.
- **틀리면 안 되는 일은 코드가, 맥락 판단은 모델이.** 위험 규칙·순서 규칙·내용 검사·법 조항 계산·증거 서명은 결정적 코드가 한다. 모델은 규칙 경보를 지울 수 없고, 낮추려면 두 판정 모델이 모두 동의해야 한다.
- **모른다는 것을 상태로 표시한다.** "기록이 없다는 것은 안전하다는 뜻이 아닙니다", `not_replayable`, "당시 정책 미확인"처럼 확인하지 못한 것을 성공이나 실패로 뭉개지 않는다.
- **바퀴를 다시 만들지 않는다.** OTLP·C2SP·DSSE·in-toto·OCSF 같은 표준에 붙이고, 직접 만든 부분은 실제 도구와의 상호운용 시험으로 확인한다. 관측 화면은 Langfuse·Phoenix에 맡기고 그 위에 검증 결과를 얹는다.
- **측정이 먼저이고, 보장은 협상하지 않는다.** 처리량은 프로파일링으로 병목을 찾아 올렸고, 영속 보장과 검증 형식은 바꾸지 않았다. 목표 미달도 숫자로 남겼다.
- **데이터 경계를 먼저 정하면 외부 자원도 쓸 수 있다.** 실제 수집 기록은 PC를 떠나지 않고, 임대 GPU에는 합성 시나리오와 공개 데이터만 보낸다.
- **사용자 피드백은 바로 화면으로.** "지금 뭐가 돌고 있는지 모르겠다", "UI가 별로", "참고 내용을 알 수 없다"가 각각 첫 화면, 다크 운영 콘솔, 세션 참고 자료로 이어졌다.

## 새 업데이트를 기록하는 법

1. 해당 분야의 `data/<분야>.json` 끝에 항목을 하나 더합니다. 번호는 같은 분야 코드의 다음 번호이고, 키는 위 표의 28개를 모두 씁니다. 역량은 `data/vocabulary.json`의 키만 씁니다.

3. `node --test test/dev-log.test.mjs`로 형식과 생성 파일이 맞는지 확인합니다(`npm test`에도 포함).
