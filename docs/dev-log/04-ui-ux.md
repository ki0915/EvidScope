### UX-01 · 첫 감사 화면: 평면 메뉴 11개, 주식형 시간축, 용도별 조회 주기

`2026-09-09` · 상태: 완료 · 계기: 계획 · 결정: AI 에이전트  
*First audit console: 11 flat menu items, stock-style timeline and purpose-based polling cadence*

**요약.** 첫 구현과 함께 감사 화면이 생겼습니다. 왼쪽 세로 메뉴 11개, 확대·이동·최신 따라가기가 되는 주식형 시간축, 근거 연결도가 들어갔습니다. 화면 자동 조회가 감사 접근 이력을 부풀리지 않도록 5초 조회를 용도별 주기(기본 1분)로 바꿔 탭당 시간당 조회를 720회에서 약 60회로 줄였습니다.

**배경.** 2026-09-09은 EvidScope가 서명 원장 기반 AI 행동 감사 파일럿으로 처음 공개된 날입니다(EL-01). 오너는 사람이 판단할 수 있는 가시성을 1순위 목표로 정했고(docs/portfolio.md), 화면은 그 목표를 직접 보여 주는 곳이었습니다. 당시 구조에서는 인증된 조회 하나하나가 서명된 감사 접근 기록으로 원장에 남았기 때문에, 화면이 자주 다시 읽을수록 감사 기록이 불어났습니다. 그래서 화면 설계가 곧 감사 기록 비용 설계였습니다. 화면은 외부 CDN 없이 정적 JavaScript와 SVG로 만들었고, 모든 값은 DOM 텍스트 노드로만 그렸습니다(public/live-graphs.js 머리말).

**계기.** 첫 구현 공개(b24f4d4)에 포함된 화면 설계. 조회 주기는 첫 시험이 5초를 기대값으로 실패한 뒤 새 기준으로 바뀐 것으로 보아 구현 중 자체 점검에서 나온 변경입니다(reports/monitoring-cadence-validation.md).

**문제.** 초기 화면은 5초마다 서버를 다시 읽도록 되어 있었습니다(첫 시험의 기대값이 5초). 탭 하나가 이론상 시간당 720번 인증 조회를 했고, 조회마다 감사 접근 기록이 남아 원장과 접근 이력이 빠르게 커졌습니다. 또 조회가 실패했을 때 옛 값을 현재 값처럼 보여 줄 위험, 숨긴 탭이나 로그아웃 뒤에도 늦게 도착한 응답이 화면을 바꿀 위험이 있었습니다. 차트 한 점의 집계 기간과 화면 갱신 주기가 섞여 있으면 짧은 급증이 긴 집계 안에 묻히는 문제도 있었습니다.

**당시 제약**

- 외부 라이브러리·CDN 없이 정적 JS·SVG로 구현
- 모든 값은 인증된 응답에서 온 텍스트 노드로만 표시(XSS 방지)
- 인증 조회마다 감사 접근 기록이 원장에 남는 당시 구조
- 합성 데이터만 사용, 실제 공급자·개인정보 없음

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 5초마다 자동 조회 유지 | 실시간처럼 보이고 구현이 단순함 | 탭당 시간당 720회 조회, 조회마다 감사 접근 기록이 쌓임, 순간 변동과 추세가 구분되지 않음 |  | 감사 기록을 조회 자체로 부풀려 감사 도구가 자기 기록을 오염시키는 구조라 버림(docs/monitoring-cadence.md) |
| 용도별 조회 범위·집계 간격·자동 조회 간격 분리(운영 기본 1시간/1분/1분, 일간 24시간/5분/5분, 주간 7일/1시간/15분, 상세 조사 10분/30초/30초) | 기본 조회를 1/12로 줄이면서 상세 조사가 필요하면 30초까지 내릴 수 있음, 추세와 순간 변동을 화면이 구분 | 새 기록이 화면에 나타나기까지 최대 1분(기본)이 걸림, 긴 집계에서 짧은 급증이 합산됨 | 선택 | 감사 접근 이력 증가를 줄이면서 용도별로 필요한 해상도를 지킬 수 있어서. 짧은 급증은 상세 조사 모드로 보도록 문서에 적음 |

**결정.** 자동 조회를 용도별 4단계 주기로 나누고, 응답이 끝난 뒤 다음 타이머를 시작하며, 실패 시 지수 백오프와 401/403 즉시 중단, 숨긴 탭·일시정지·화면 이탈·로그아웃에서는 조회를 멈추고 늦은 응답을 버린다. 이유: 감사 화면이 조회 자체로 감사 기록을 부풀리지 않게 하고, 실패·지연 상태를 정직하게 보여 주기 위해

**한 일**

1. 왼쪽 사이드바에 평면 메뉴 11개(행동 조사함·에이전트 목록·가시성 그래프·관측 개요·증거 탐색·탐지 경보·사건·탐지 룰·거버넌스 검토·보존·수집 건강)를 둔 정적 화면 구성(public/index.html, public/app.js 855줄)
2. 주식 차트식 시간축 구현: 우측 수치축, 확대·축소, 이전·다음 구간, 시간축 슬라이더, 전체 기간 미니 차트, 최신 따라가기, 사이드바를 숨기는 넓게 보기(public/live-graphs.js). 가짜 가격이나 OHLC 캔들은 만들지 않음
3. 막대를 누르면 해당 표본 행동만 남는 필터와, 행동 상세에서 요청·실행·독립 결과·권한 기록과 참고자료 버전을 잇는 근거 연결도 추가
4. 조회 주기 표를 docs/monitoring-cadence.md에 문서화하고, 마지막 구간은 미완성, '최근 5분 수신'은 장애 기준이 아닌 참고 상태라고 화면·문서에 명시
5. 응답 완료 후 타이머 시작, 실패 시 2·4·8배 백오프(최대 1시간), 401/403 자동 재시도 중단, 숨김·이탈 시 이전 비동기 응답 폐기 구현
6. 에이전트 목록에 분자·분모와 평가 범위를 함께 표시하고 미확인은 '산정 불가'로 표시(준수율이 법적 준수율이 아니라는 문구 포함)
7. monitoring·monitor-ui 테스트 4개와 순수 합성 DOM 검사 10개 작성, 실제 브라우저에서 1분·15분 갱신과 일시정지·재개 확인

**결과.** 탭 하나의 기본 자동 조회가 시간당 720회에서 약 60회로 줄었고, 조회 주기·백오프·탭 숨김 정지가 테스트 4/4와 DOM 검사 10/10으로 확인됐습니다. 실제 로컬 화면에서 주간 41건, 1시간 12건(성공 6, 실패 6)의 합성 기록이 표시됐습니다. 대규모 보존량에서의 7일 조회 성능과 출처별 기대 수신 주기·알림 SLA는 검증하지 않았습니다.

**트레이드오프와 남은 한계**

- 기본 모드에서 새 기록이 화면에 나타나기까지 최대 1분 지연
- 긴 집계 구간은 짧은 급증을 합산해 숨길 수 있어 상세 조사 모드를 따로 봐야 함
- '최근 5분 수신'을 장애 기준으로 쓰지 않기로 해 출처별 heartbeat·알림 SLA는 비어 있음
- 메뉴 11개를 평면으로 나열해 기능이 늘수록 길어지는 구조(UX-04에서 재구성)

**배운 점**

- 감사 도구에서는 화면 조회도 감사 기록이므로, 갱신 주기는 UX 문제이자 기록 비용 문제다
- 실패나 지연을 숨기지 않는 것(마지막 성공 시각 유지, 미완성 구간 표시)이 실시간처럼 보이는 것보다 감사 화면에 맞다

**다시 생각해 볼 질문**

- 접근 기록이 원장 밖 봉인 로그로 옮겨진 뒤(EL-10)에도 기본 1분 주기가 여전히 맞는 값인가, 아니면 더 짧게 해도 기록 비용이 감당되는가?
- 실제 감사인이 쓰는 시간대 분포를 재 보면 주간 15분 갱신 같은 값은 바뀌어야 할까?
- '최근 5분 수신' 참고 표시 대신 출처별 기대 주기를 등록받았다면 미수집을 더 일찍 알아챘을까?

**다른 선택을 했다면**

- 처음부터 서버 푸시(SSE)로 만들었다면 조회마다 남는 접근 기록 문제는 사라졌겠지만, 연결 유지 비용과 인증 만료 처리가 새 과제가 됐을 것입니다(추정).

**다시 볼 시점.** 실제 감사인이 여러 명 동시에 화면을 쓰거나, 보존 기록이 7일 조회 성능을 위협할 만큼 커질 때

**이력서 문장**

- 감사 화면 자동 조회가 감사 접근 기록을 부풀리지 않도록 용도별 조회 주기·지수 백오프·숨긴 탭 정지를 설계해 탭당 조회를 시간당 720회에서 약 60회(1/12)로 줄임
- (EN) Designed purpose-based polling, exponential backoff and hidden-tab pause for an audit console so screen refreshes stopped inflating the audit trail, cutting per-tab queries from 720 to about 60 per hour.

**예상 면접 질문**

- Q. 왜 실시간 화면을 5초 조회로 두지 않았나요?
  - 당시 인증된 조회마다 감사 접근 기록이 원장에 남아 5초 조회는 탭당 시간당 720건의 기록을 만들었다
  - 용도별로 조회 범위·집계 간격·갱신 간격을 나눠 기본 1분, 상세 조사 30초로 했다
  - 실패 시 옛 값을 현재 값처럼 보이지 않게 마지막 성공 시각을 유지하고 백오프했다
- Q. 주식형 차트를 감사 화면에 쓴 이유와 한계는?
  - 확대·이동·최신 따라가기로 시간 구간을 오가며 행동 수 변화를 보게 했다
  - 가짜 가격이나 캔들은 만들지 않고 수신 건수만 보여 준다
  - 긴 구간은 짧은 급증을 합산하므로 상세 조사 모드와 함께 보도록 했다

### UX-03 · AI 검토 지원 화면: 기계 초안과 사람 판단을 화면에서 분리

`2026-09-09` · 상태: 완료 · 계기: 계획 · 결정: AI 에이전트  
*AI review-assistance screen that keeps machine drafts apart from human decisions*

**요약.** 로컬 AI가 사건 근거로 초안을 쓰고 사람이 채택·수정·반려하는 'AI 검토 지원' 화면을 3단계 흐름으로 만들었습니다. 초안이 승인·정책 점수·법적 결론으로 읽히지 않도록 화면 문구와 구조(고정된 근거, 기계 초안, 사람의 검토 3열)로 막았습니다. 실제 Qwen3 4B 실행 초안은 인용이 주장을 뒷받침하지 못해 시험상 반려로 기록됐습니다.

**배경.** 첫 공개 날 로컬 AI 자문(advisory) 파이프라인과 신뢰 경계가 정해졌습니다(JM-01, EL-02). 모델은 사건 자료를 받아 초안만 쓰고 결정은 사람이 한다는 원칙이었고, 이 화면은 그 원칙을 사용자가 직접 마주하는 곳이었습니다. 당시 팀 구성은 설계·감사 Astra, 핵심 구현 Sol, UI는 Claude였고 이 화면은 Claude가 쓴 UI 초안입니다(docs/portfolio.md, 커밋 제목). 자격 증명 파일로 로컬 CLI가 모델을 실행하는 구조라, 화면에서 자격 증명을 어떻게 다룰지도 함께 정해야 했습니다.

**계기.** 로컬 AI 자문 파이프라인(JM-01)의 사람 쪽 화면. Claude가 UI 담당으로 구현(300c07f 제목 'Claude-authored').

**문제.** 로컬 AI가 쓴 초안이 화면에 그대로 뜨면 승인, 정책 점수, 실행 게이트, 법적 결론처럼 읽힐 위험이 있었습니다. 근거 없이 초안을 요청할 수 있으면 모델이 빈 근거로 그럴듯한 결론을 만들 수 있었습니다. 실행 자격 증명이 화면 메모리에 남거나 여러 번 내려받을 수 있으면 유출 경로가 됩니다. 또 초안을 쓴 뒤 사건 근거가 바뀌면 초안이 낡은 근거에 기대게 됩니다.

**당시 제약**

- 추가 API 비용 0원, 로컬 모델(Qwen3 4B)만 사용
- 모델 실행은 사람이 명시적으로 시작해야 함(자동 실행 금지)
- 합성 데이터로만 시험, 실제 사람의 내용 검수 없음
- 기존 app.js의 전역 범위에 기대지 않는 모듈 연결

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 초안 결과를 사건 판단·정책 점수에 바로 반영 | 사람 작업이 줄어 보임 | 기계 출력이 사람 판단과 섞여 책임 소재가 사라짐 |  | 초안의 채택·수정·반려 기록은 기존 사건 판단이나 정책 점수를 덮어쓰지 않는다는 원칙(docs/feature-guide.md) |
| 사건 화면에서 버튼 한 번으로 모델 자동 실행 | 빠름 | 사람이 근거를 고르지 않은 채 실행되고, 자격 증명이 서버·화면에 상주함 |  | 로컬 실행 전달은 사람이 명시적으로 시작하는 조치로 두고, 자격 증명을 내려받아 로컬 CLI로 직접 시작하게 함 |
| 사건·역할 선택, 근거 선택, 로컬 실행 전달의 3단계 흐름과, 고정된 근거·기계 초안·사람의 검토를 나란히 보여 주는 상세 화면 | 단계마다 사람이 무엇을 넘기는지 보이고, 초안과 판단이 화면에서 구분됨 | 단계가 많아 느림 | 선택 | 기계 초안과 사람 판단을 구조로 분리하는 것이 이 화면의 목적이라서 |

**결정.** AI 검토 지원을 3단계 흐름으로 만들고, 근거가 없으면 요청을 만들 수 없게 하며, 제출 시점 근거 스냅샷과 해시를 함께 보여 주고, 화면 곳곳에 '기계 출력은 사람의 승인이 아니다'를 적는다. 자격 증명은 한 번만 내려받고 메모리에서 즉시 지운다. 이유: AI 초안이 승인이나 법적 결론으로 오인되는 것을 화면 문구가 아니라 흐름 자체로 막기 위해

`2026-10-06` · 상태: 대체됨 · 계기: 계획 · 결정: AI 에이전트

**요약.** 기능이 늘며 13개까지 늘어난 평면 메뉴를 현황, AI 자산·수집, 탐색·조사, 거버넌스, AI 검토실, 운영·설정의 6개 업무 묶음과 그 안의 하위 탭으로 바꿨습니다. 09-12 1차 완성본 계획의 '사용자 중심 UI' 절을 구현한 것으로, 큰 숫자 카드 대신 실제 조사 목록과 관측 공백을 앞에 두는 원칙을 세웠습니다. 이 메뉴 구조는 10-15 다크 운영 콘솔(UX-12)에서 다시 바뀌었습니다.

**배경.** 09-09 첫 화면 뒤 AI 검토 지원과 에이전트 팀이 붙어 평면 메뉴가 13개가 됐습니다(UX-03). 09-12 1차 완성본 실행 계획(EL-03)은 6절 '사용자 중심 UI'에서 Datadog의 facet·목록 옆 상세 패널과 Grafana의 시간 범위·단계별 drilldown을 업무 흐름에 맞춰 적용하자고 정했습니다. 실제 구현은 PC 작업본에서 이뤄졌고, 10-06 파일럿 v0.1.0 공개 커밋(28d4dfb)과 함께 저장소에 들어왔습니다(EL-05). 같은 시기 모델 실행 상태, OIDC 로그인, 금융 증거 화면도 늘어 메뉴를 정리하지 않으면 '지금 무엇을 해야 하는지'가 보이지 않는 상황이었습니다.

### UX-05 · 통제 화면 추가: 에이전트 등록부, 승인함, 정지 버튼, 카탈로그 가져오기, 보존 회전, 외부 trace 링크

`2026-10-07 → 2026-10-08` · 상태: 완료 · 계기: 오너 요청 · 결정: 오너와 AI 에이전트  
*Control screens: agent registry, approval queue, stop button, catalog import, retention rotation and external trace links*

**요약.** 오너가 요청한 GRC 대시보드 설계(10-07)를 구현하며 등록부·승인함·정지 버튼과 전파 패널·카탈로그 가져오기·보존 회전 화면을 이틀에 걸쳐 붙였습니다. 권한·4-eyes·게이트는 서버가 지키고 화면은 서버 값을 텍스트로만 그리는 원칙을 세웠습니다. 실행 추적(trace) 화면은 직접 만들지 않고 Langfuse·Phoenix의 같은 trace로 여는 링크를 달았습니다.

**배경.** 10-07 오너는 사내에 흩어진 미완성 AI 에이전트를 위한 관리자용 GRC(거버넌스·위험·컴플라이언스) 대시보드를 설계해 달라고 했고, 메뉴 트리·감사 증적 스키마·실시간 차단·격리 구조를 요구하며 Langfuse, Credo AI, watsonx.governance, Monitaur, Phoenix, Logfire, Traccia 등 7개 참고 제품을 줬습니다(작업 메모). 답으로 나온 설계는 EvidScope를 '증거와 통제 계층'으로 두고, 추적 화면은 Langfuse·Phoenix에, 호출 가로채기는 게이트웨이에, 허용 판단은 OPA·Cedar에 맡기며, EvidScope는 사람 승인일 때만 실행 경로에 들어간다는 것이었습니다. 3·4·5·7라운드가 이 설계의 구현 순서를 따랐고(EL-15, EL-16, EL-17, EL-19, EL-21), 이 항목은 그 서버 기능에 붙은 화면들입니다.

**계기.** 오너의 GRC 대시보드 설계 요청(10-07)과 그 설계의 구현 순서를 따른 3~7라운드. 화면은 각 라운드의 서버 기능과 함께 추가.

**문제.** 레지스트리·승인 대기열·정지 명령·카탈로그 가져오기·보존 회전이 API로만 있으면 사람이 상태를 확인하고 결정할 수 없었습니다. 동시에 화면이 권한 판단을 하면 화면 조작으로 4-eyes(두 사람 승인)나 게이트를 우회할 위험이 생깁니다. 승인 요청은 남은 시간이 지나면 거부되므로 대기 중인 요청이 묻히면 안 됐습니다. 실행 추적 화면을 따로 만들면 이미 성숙한 관측 도구를 다시 만드는 일이 됩니다.

**당시 제약**

- 역할·4-eyes·게이트 검사는 서버에서만
- 화면은 서버 응답을 DOM 텍스트 노드로만 표시
- EvidScope는 아무것도 차단하지 않음(정지는 기록이며 집행 지점이 받아 가야 효력)
- 외부 링크는 https만, 새 탭, referrer 없음

### UX-07 · 학습 데이터 검토 큐와 실험 비교 화면

`2026-10-08` · 상태: 완료 · 계기: 오너 피드백 · 결정: 오너와 AI 에이전트  
*Training-data review queue and experiment comparison screens*

**요약.** 거버넌스 매핑 학습 데이터 초안을 TSV 시트로 검토하던 방식을, 한 행씩 보여 주고 A·R·N·P 단축키로 승인·거절하는 화면 큐로 바꿨습니다. 기준선·기본 모델·어댑터 후보를 고정 평가 세트에서 나란히 보는 실험 비교 탭과 서명된 팩트시트 목록도 넣었습니다. 화면 클릭이 곧바로 학습 파일을 바꾸지 않도록 결정은 서명된 원장 기록으로 남기고 학습 파일은 따로 만들게 했습니다.

**배경.** 7라운드에서 오너는 로컬 모델을 '제대로 학습'시켜 거버넌스 지원 워커로 쓰자고 했고, 과제는 증거 한 건을 규제 항목 ID로 잇는 거버넌스 매핑으로 정해졌습니다(JM-04). 같은 날 오너는 예전에 보낸 유사 제품들을 하나도 반영하지 않은 것 같다고 지적했고, Claude는 연결만 했지 작동 방식은 가져오지 않았다고 인정했습니다(작업 메모). 그 결과 합의한 순서에 Langfuse 방식의 화면 검토 큐(TSV 대체), Langfuse·Phoenix 방식의 실험 비교, watsonx 방식의 서명된 학습 팩트시트가 들어갔습니다. 이 항목은 그중 화면 부분입니다.

**계기.** 오너가 참고 제품의 작동 방식이 반영되지 않았다고 지적(10-08 06:38Z). 그 갭 목록에서 화면 검토 큐와 실험 비교가 나옴.

> "기존에 내가 보내줬던 유사 프로젝트 ... 반영을 하나도 안한거 같더라?"

**문제.** 사람 검토가 TSV 시트에서 이뤄져 누가 언제 어떤 행을 승인했는지 서명된 기록이 남지 않았고, 시트를 고치면 학습 데이터가 바로 바뀌었습니다. 기준선·기본 모델·어댑터 후보의 점수를 비교하려면 보고서 파일을 따로 열어야 했습니다. 학습·평가·승격 실행이 어떤 데이터와 설정으로 돌았는지 남기는 공식 기록도 없었습니다.

**당시 제약**

- 검토자·관리자만 결정 가능, 감사인은 조회만
- 결정은 행의 검토 대상 내용 해시에 묶인 서명 기록
- 학습 파일은 검증된 감사 내보내기에서만 생성
- 셰이크다운(시운전) 실행은 승격 불가

**검토한 대안**

**한 일**

### UX-08 · 검토 화면을 쉬운 말로: 한국어 번역, 쉬운 설명, 예/아니오 질문

`2026-10-10` · 상태: 완료 · 계기: 오너 피드백 · 결정: AI 에이전트  
*Plain-language review screen: Korean translations, plain explanations and yes/no questions*

**요약.** 검토 화면에 영어 문장, 요구사항 ID, 해시만 보여 검토자가 어떻게 판단할지 모르던 문제를 고쳤습니다. 행마다 한국어 참고 번역, 요구사항이 묻는 것의 쉬운 설명, 매핑마다 예/아니오 질문, 사용법 카드를 붙이고, 질문을 '법을 지켰다는 증거인가'에서 '이 요구사항을 확인하는 사람이 이 문서를 꺼내 볼 것인가'로 바꿨습니다. 보조 정보는 표시 전용이라 데이터셋·행 해시·결정에 섞이지 않습니다.

**배경.** UX-07에서 만든 학습 데이터 검토 큐는 동작했지만, 실제로 화면을 연 검토자는 행을 보고 무엇을 근거로 승인·거절해야 할지 몰랐습니다(2f7f3ac 본문). 행에는 영어 증거 문장, 요구사항 ID, 해시가 보였고, 인공지능기본법·EU AI Act·ISMS-P 조항을 외우고 있지 않으면 판단이 어려웠습니다. 이틀 사이 거버넌스 매핑 파일럿(JM-05)이 PC에서 돌기 시작해 사람 검토가 필요한 시점이었습니다.

**계기.** 검토자가 행을 보고 어떻게 결정해야 할지 몰랐고, 질문을 “이 로그가 법을 지켰다는 증거인가”로 읽었다는 피드백(2f7f3ac, 8ceb628 본문). 검토자는 오너로 보입니다(추정).

**문제.** 검토자가 본 것은 영어 문장, 요구사항 ID, 해시뿐이라 판단 기준이 없었습니다. 질문이 '준수 판정'처럼 읽혀, 증거를 요구사항 폴더에 분류하는 일이 법적 판단을 내리는 일처럼 느껴졌습니다. 이대로라면 검토 결과가 들쭉날쭉하거나, 검토자가 판단을 포기해 큐가 멈출 위험이 있었습니다.

**당시 제약**

- 보조 정보가 데이터셋·행 해시·결정에 섞이면 안 됨
- AI 기본법 항목은 요구사항 카탈로그 문장 사용, EU AI Act·ISMS-P 요약은 Claude가 작성
- 검토자는 규정 전문가가 아닐 수 있음

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| ID·해시 중심 화면 유지 + 별도 매뉴얼 문서 | 화면 변경 없음 | 검토자가 화면과 문서를 오가야 하고 판단 기준이 여전히 불분명 |  | 검토자가 화면에서 바로 판단하지 못한다는 문제가 그대로 남음 |

### UX-09 · 경보 목록의 '관련 기준' 칸: 붙이고 나서 한 줄 항목 번호로 압축

`2026-10-15` · 상태: 완료 · 계기: 오너 피드백 · 결정: AI 에이전트  
*Related-criteria column on alerts, then compressed to one line of item numbers*

**요약.** 에이전트 위험 경보마다 그 경보를 증거로 볼 수 있는 ISMS-P·인공지능기본법·EU AI Act 항목을 '관련 기준' 칸으로 붙였습니다. 처음에는 항목 제목을 모두 나열해 경보 하나가 약 20줄을 차지했기 때문에, 같은 날 기준별 한 줄의 항목 번호로 줄이고 제목은 마우스를 올리면 보이게 했습니다. '판정이 아니다'라는 설명 문구는 표 아래에서 위로 옮겼습니다.

**배경.** 10-15 오너는 '수집·탐지 먼저'로 방향을 바꿨고(AM-01), Claude Code hook으로 실제 기록이 들어오며 위험 규칙 경보가 생기기 시작했습니다(AM-02). 같은 날 새벽 오너는 '어떤 기준으로 감사를 수행하는지 모르겠다'고 했습니다(작업 메모). 그때까지 에이전트 위험 규칙 경보는 어떤 요구사항의 증거로도 세지지 않았고, 화면은 경보가 어떤 조항과 관련되는지 보여 주지 않았습니다. 대응표 v3(AM-03)가 그 연결을 만들었고, 이 항목은 그 연결을 화면에 보이는 방식입니다.

**계기.** 오너가 감사 기준이 보이지 않는다고 함(10-15 04:11Z). 칸을 붙인 뒤 목록이 너무 길어진 것은 같은 날 자체 확인으로 발견(1dbe574 본문).

**문제.** 경보 목록에서 경보가 어떤 조항과 관련되는지 보이지 않아, 감사 기준이 무엇인지 오너가 알 수 없었습니다. 칸을 붙인 첫 버전(987223e)은 관련 항목을 전체 제목과 함께 모두 나열해 에이전트 위험 경보 하나가 약 20줄을 차지했습니다. 경보 몇 개만 있어도 화면이 조항 제목으로 가득 차 훑어보기가 불가능했고, '준수 판정이 아니다'라는 설명은 표 아래에 있어 먼저 읽히지 않았습니다.

**당시 제약**

- 경보와 조항 연결은 서명된 대응표(v3)에서만 계산, 모델이 쓰지 않음
- '증거가 놓일 곳'이지 준수·위반 판정이 아니라는 점을 먼저 보여야 함
- 감사인은 번호만으로 항목을 알아보지만 비전문가는 제목이 필요함

| 무결성 검사를 표본 검사로 줄여 빠르게 | 응답이 빨라짐 | 전체 재대조라는 검사 의미가 사라짐 |  | 기다리는 동안 무엇을 하는지 보여 주고 결과를 한 줄로 먼저 보여 주는 쪽을 택함 |

**결정.** 자산 등록에 '합성(데모·시험)' 표시를 추가해 경보를 data=real|synthetic으로 거르고 기본은 실제 기록만 보여 주며, 보존 API는 검토 순서 앞 200건과 전체 건수만 보내고, 무결성 검사는 진행 안내 뒤 한 줄 요약을 먼저 보여 준다. 이유: 서명 원장을 건드리지 않고 실제 경보를 드러내며, 무거운 화면을 가볍게 하되 검사의 의미는 지키기 위해

**한 일**

1. 자산 등록 폼에 '기록 종류: 실제 업무 / 합성(데모·시험)' 선택을 추가하고, 데모 스크립트가 데모 자산을 합성으로 등록하게 함
2. 경보 화면에 '기록: 실제 기록 / 합성(데모·시험) 기록 / 전체' 선택(기본 실제), 합성 경보에 '합성' 배지, 화면 설명 문구 추가
3. 현황의 경보 수를 합성을 뺀 숫자로 바꾸고 '실제 기록의 위험 신호 · 합성(데모) N건 제외' 설명 표시
4. GET /api/retention에 limit(기본 200)과 counts를 넣어 '계획에 넣을 수 있는 것·보존이 먼저 끝나는 것부터 200건'과 전체 건수만 표시
5. 무결성 검사 버튼을 누르면 '서명 원장 전체와 보관 사본을 처음부터 다시 대조하고 있습니다' 안내 뒤, '검증 통과: 서명 원장 N건, 보관 이벤트 N건, 평가 N건을 대조했습니다 (N초)' 한 줄과 상세 JSON 순으로 표시
6. PC의 9월 데모 자산을 합성으로 표시(되돌리기 옵션 포함), 14개 파일 해시 대조 후 반영, 브라우저로 현황·경보·보존·무결성 화면 확인

**결과.** 경보 화면이 기본으로 실제 기록 6개만 보여 주게 됐고, 그 6개는 모두 PC의 Claude Code 기록에서 나온 위험 탐지였습니다. 데모 경보 63건과 서명 원장은 그대로 남았습니다. 보존 화면 응답은 약 1/9로 줄었고, 무결성 검사는 약 3.7초 그대로지만 기다리는 동안 무엇을 하는지와 결과 요약이 먼저 보이게 됐습니다.

**결정.** 기본 어두운 테마의 운영 콘솔(대시보드·로그 탐색·실시간 보기)을 새 첫 화면으로 하고, 메뉴를 모니터링·조사·거버넌스·설정 4개 그룹으로 다시 묶으며, 기존 화면은 자동 생성한 어두운 테마로 옮긴다. 실시간 보기는 2초 폴링, 자동 분류는 조회 시점의 읽기 도움으로 둔다. 이유: 오너가 원한 Datadog/Grafana식 모니터링 경험을 하루 안에 실제 PC에서 보여 주면서, 판정이 아닌 것을 판정처럼 보이게 하지 않기 위해

2. 대시보드(public/ops.js): 수집된 기록·AI 도구 호출·세션·위험 행동·실패한 호출·열린 경보 6개 타일(작은 추이선), 에이전트별 활동 막대(Claude Code·Codex 색 고정), 에이전트별 수집 상태(마지막 수신, 과거 기록 가져오기 수, 제외한 합성 기록 수), 위험·실패 추이, 분류별 AI 행동, 많이 걸린 탐지 규칙, 최근 위험 신호, 최근 세션, 맨 아래 '관측·판단의 한계'. 기간 15분~30일 6단계(기본 24시간), 자동 새로고침 끔·10초·30초(기본)·1분, 숨긴 탭에서는 건너뜀
3. 로그 탐색: 검색 문법(단어, -단어 제외, 구절, 필드:값, / 키로 바로 입력), 왼쪽 facet 8종(에이전트·분류·기록 종류·상태·위험·수집 방식·데이터·행위자), 기간별 30~60개 막대의 시간 히스토그램(막대를 누르면 그 구간으로 확대), 행을 누르면 그 자리에서 상세가 펼쳐지고 '행동 조사 열기'·'같은 세션 기록 보기'·'같은 분류만 보기' 버튼
4. 실시간 보기: 켜면 2초마다 마지막으로 본 원장 번호 이후 기록을 최대 200건씩 받아 목록 맨 위에 붙이고 '실시간 +N' 표시, 목록은 최대 500행 유지, 화면을 떠나거나 끄면 멈춤
5. 행동 상세에 '세션 참고 자료' 추가: 같은 세션에서 이 행동보다 먼저 에이전트가 읽거나 검색했다고 보고한 파일·웹·도구(최대 40개)와 '실제로 판단에 사용했는지는 확인하지 않습니다' 문구
6. 서버 src/log-explorer.mjs(416줄): /api/dashboard·/api/logs, 조회 시점 자동 분류, facet·버킷 집계, 스캔 상한. 분류는 저장·서명·평가 엔진에 쓰지 않음

8. '판정 아님', '기록이 없다는 것은 안전하다는 뜻이 아닙니다', '수집되지 않은 행동은 0으로 보입니다. 미관측은 안전이 아닙니다' 문구를 빈 결과와 패널 하단에 배치. log-explorer 테스트 추가, PC에 29개 파일 해시 대조 후 반영
