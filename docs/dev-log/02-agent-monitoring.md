<a id="am-01"></a>
### AM-01 · 방향 전환: 학습보다 수집·탐지 먼저

`2026-10-15` · 상태: 완료 · 계기: 오너 피드백 · 결정: 오너  
*Change of direction: collection and detection before more model training*

**요약.** 오너가 “위협도 감사도 아무것도 안 되는 것 아니냐”고 지적하자, 거버넌스 매핑 모델 학습을 배경 작업으로 돌리고 오너 PC의 실제 AI 도구 기록을 받아 위험을 표시하는 일을 먼저 하기로 했다. 약속한 순서는 실제 기록을 AI 기본법·ISMS-P 증거로 잇기, Codex 연결, 여러 행동을 엮은 이상 탐지였고, 이후 AM-02~AM-05가 그 순서대로 하루 안에 만들어졌다.

**배경.** 10-15 아침까지 프로젝트의 중심은 증거 문장을 규제 항목 ID에 붙이는 거버넌스 매핑 모델 학습이었다. 파일럿 13까지 돌렸지만 어느 것도 게이트를 넘지 못했고, 오너는 같은 날 목표를 99%로 올리면서 “어떤 기준으로 감사를 수행하는지 모르겠다”고 말했다. 오너가 AI가 시스템 비밀번호 파일 같은 민감 파일 읽기를 탐지하느냐고 묻자, 그런 기본 규칙이 없고 모델도 위협 탐지기가 아니라는 답이 돌아갔다. 증거 계층(서명 원장, 재생, 증거 묶음)은 9~10월 라운드로 갖춰져 있었지만 PC의 어떤 AI 도구도 기록을 보내지 않아 화면에 실제 활동이 하나도 없었다.

**계기.** 10-15 오너가 학습 진행 상황을 보다가 제품이 실제로는 아무것도 감시하지 못한다고 지적했다. 직전에 민감 파일 읽기를 탐지하느냐는 질문에 ‘아니다’라는 답을 받은 뒤였다.

> "위협도 감사도 아무것도 안되는 거 아니야?"

**문제.** PC의 어떤 AI 도구도 EvidScope로 기록을 보내지 않았다. 기존 개발용 수집기는 도구 종류(셸, 파일 읽기)만 남겨서 무엇을 읽었는지 구분하지 못했다. 규칙은 행동 하나씩만 판단했고, 여러 행동을 엮는 규칙은 ‘한 행위자가 10분에 3번 이상 거부됨’ 하나뿐이었으며 민감 파일 경로 규칙도 없었다. 학습 중인 모델은 증거 문장을 조항에 붙이는 일만 했기 때문에 위협을 찾아 주지 못했다.

**당시 제약**

- 실제 기록은 오너 PC 밖으로 내보내지 않음
- AI 도구의 작업을 방해하면 안 됨(오너가 매일 쓰는 도구)
- 1인 개발, AI 코딩 에이전트가 구현
- 기존 서명 원장·재생 구조를 깨지 않아야 함

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 거버넌스 매핑 모델 학습을 계속해 99% 목표에 먼저 도달 | 이미 만든 학습 파이프라인과 271문항 시험을 그대로 이어 쓸 수 있음 | 모델이 위협 탐지기가 아니라서 학습이 성공해도 ‘무엇이 위험한가’는 여전히 답하지 못함, 파일럿 13까지 게이트 미통과 |  | 오너가 보기에 보여 줄 수 있는 실제 기능이 없었음 |
| 실제 AI 도구 기록 수집과 규칙 탐지를 먼저 하고 학습은 배경에서 계속 | 하루 안에 오너 자신의 도구에서 나온 실제 경보를 보여 줄 수 있음, 이후 모델이 넘어야 할 규칙 기준선이 생김 | 모델 학습 진척이 늦어짐 | 선택 | 오너가 카드에서 ‘수집·탐지 먼저’를 고름 |

**결정.** 학습은 배경으로 돌리고 실제 기록 수집과 위험 탐지를 먼저 한다. 순서는 실제 기록을 법·인증 증거로 잇기, Codex 연결, 여러 행동 이상 탐지. 이유: 보여 줄 수 있는 실제 탐지가 먼저 있어야 제품이 의미가 있다고 판단했다.

**한 일**

1. PC에서 실제로 기록을 보내는 AI 도구가 없다는 점과 기존 수집기의 한계(도구 종류만 기록)를 확인
2. 오너에게 수집·탐지 우선 여부를 카드로 묻고 ‘수집·탐지 먼저’ 선택을 받음
3. Claude Code hook 추가 여부를 묻고 ‘추가’ 선택을 받음(AM-02)
4. Codex hook 추가 여부를 묻고 ‘추가’ 선택을 받음(AM-04)
5. 실제 기록을 법·인증 증거로, Codex, 여러 행동 이상 탐지 순서로 작업 계획을 약속

**결과.** 같은 날 Claude Code hook(AM-02), 대응표 v3(AM-03), Codex hook(AM-04), 평가 엔진 v5 순서 규칙(AM-05)이 차례로 만들어져 약속한 세 단계가 하루 안에 끝났다. 학습은 이후 위협 시나리오 기반 세션 판정(JM 트랙)으로 다시 설계되어 이어졌다.

| 지표 | 전 | 후 | 단위 | 범위 | 출처 |
|---|---|---|---|---|---|
| EvidScope로 기록을 보내는 PC의 AI 도구 수 | 0 | 2(Claude Code, Codex) | 개 | 오너 PC, 10-15 하루 동안 | 작업 메모 |
| 여러 행동을 엮는 규칙 수(전환 시점) |  | 1(한 행위자 10분 3회 이상 거부) | 개 | 전환 결정 시점의 평가 엔진 | 작업 메모 |

**트레이드오프와 남은 한계**

- 거버넌스 매핑 모델의 99% 목표 달성은 뒤로 미룸
- hook 기록은 AI 도구 안에서 나오는 자기 보고라 독립 관측은 여전히 없음

**배운 점**

- 기술적으로 쌓은 것이 많아도 사용자가 자기 환경에서 실제 결과를 못 보면 제품이 없는 것과 같다.
- 모델이 하는 일(증거를 조항에 붙이기)과 사용자가 기대하는 일(위협 탐지)이 다를 수 있으니 처음부터 맞춰 봐야 한다.

**다시 생각해 볼 질문**

- 학습을 멈추지 않고 수집과 병행했다면 거버넌스 매핑 모델이 세션 판정으로 재설계되는 시점이 더 빨랐을까, 늦었을까?
- 처음부터 hook 수집을 첫 기능으로 잡았다면 9~10월 증거 계층 라운드의 우선순위가 어떻게 달라졌을까?
- PC 한 대에서 보여 주는 실제 탐지와 회사 내부망 감사라는 최종 목표 사이의 거리를 어떤 순서로 좁혀야 할까?

**다른 선택을 했다면**

- 학습을 계속했다면 99% 목표에 매달린 채 PC에서는 여전히 아무 경보도 볼 수 없었을 것이다(추정).

**다시 볼 시점.** 회사 내부망 여러 호스트로 확장할 때, 수집과 모델 개발의 우선순위를 다시 정할 때

**이력서 문장**

- “아무것도 안 되는 것 아니냐”는 사용자 피드백에 모델 학습을 뒤로 미루고 실제 AI 도구 기록 수집·탐지로 방향을 바꿔, 하루 안에 AI 에이전트 2종 실시간 수집과 위험 규칙 경보를 PC에서 동작시킴

<a id="am-02"></a>
### AM-02 · Claude Code hook 실시간 수집과 기본 위험 규칙 50개

`2026-10-15` · 상태: 완료 · 계기: 오너 요청 · 결정: 오너와 AI 에이전트  
*Live Claude Code hook collection and a 50-rule baseline risk pack*

**요약.** Claude Code가 도구를 쓰기 직전과 직후에 실행되는 hook이 각 호출을 서명된 기록으로 EvidScope에 보내도록 했다. 대상(경로·명령·URL)까지 담아 기존 사용자 규칙 엔진 위에서 위험 규칙 50개가 경보를 내고, hook은 절대 작업을 막거나 실패시키지 않게 설계했다.

**배경.** AM-01에서 수집·탐지를 먼저 하기로 정한 직후의 첫 구현이다. EvidScope에는 서명된 수집 계약, agent·tool 같은 출처 구분, 검토자 작성과 관리자 승인을 거치는 사용자 규칙 엔진이 이미 있었다. 빠진 것은 실제 AI 도구에서 대상까지 담은 기록을 받아 오는 수집기와 민감 행동을 가르는 기본 규칙이었다. 오너는 Claude Code를 실제 업무에 매일 쓰고 있었기 때문에 수집이 붙으면 바로 실제 기록이 흐를 수 있었다.

**계기.** AM-01 결정 뒤 오너가 Claude Code 설정에 hook을 ‘추가’하는 선택지를 골랐다.

**문제.** 기존 개발 수집기는 도구 종류만 남겨 시스템 비밀번호 파일을 읽은 것과 README를 읽은 것을 구분하지 못했다. AI 도구가 무엇을 읽고, 실행하고, 어디로 보냈는지가 기록되지 않아 위험 규칙을 걸 대상이 없었다. 또 hook이 잘못 동작하면 오너가 쓰는 AI 작업 자체가 멈출 수 있었다.

**당시 제약**

- hook이 AI 작업을 막거나 느리게 하거나 실패시키면 안 됨
- 명령 속 비밀번호·토큰은 저장하지 않아야 함
- 기록은 오너 PC의 EvidScope에만 저장
- Node.js 내장 모듈만 사용(무의존성), 한글·공백 경로가 hook 명령줄에 들어가지 않게

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 기존 개발 수집기를 그대로 사용 | 추가 작업 없음 | 도구 종류만 남아 대상이 없으므로 위험 규칙을 걸 수 없음 |  | 무엇을 읽고 보냈는지 모르면 탐지가 불가능 |
| Claude Code의 실행 전·후 hook으로 대상까지 담은 서명 기록 전송 | 도구 호출마다 행위자·도구·행동 분류·대상·목적지·결과가 남음, 기존 수집 계약과 규칙 엔진 재사용 | AI 도구 안에서 도는 자기 보고라 독립 관측이 아님 | 선택 | 하루 안에 실제 기록과 경보를 볼 수 있는 가장 짧은 길 |

**결정.** 실행 전 hook은 intent 기록(행위자, 도구, 행동 분류, 대상, 목적지)을, 실행 후 hook은 결과(성공·실패) 기록을 보낸다. hook은 아무것도 출력하지 않고 항상 정상 종료하며 EvidScope가 꺼져 있으면 대기열에 둔다. 위험 규칙 50개를 검토자 작성·관리자 승인으로 올린다. 이유: 탐지에 필요한 대상 정보를 얻으면서도 오너의 AI 작업을 절대 방해하지 않기 위해서다.

**한 일**

1. scripts/claude-code-hook.mjs: 실행 전·후 hook, HMAC 서명 수집 요청, 1초 시간 제한, 최대 5MiB 로컬 대기열과 다음 호출 때 최대 20건 재전송

<a id="am-03"></a>
### AM-03 · 대응표 v3: 에이전트 경보를 ISMS-P·인공지능기본법·EU AI Act 항목에 연결

`2026-10-15` · 상태: 완료 · 계기: 오너 피드백 · 결정: AI 에이전트  
*Mapping v3: linking AI agent alerts to ISMS-P, Korean AI Basic Act and EU AI Act items*

**요약.** 에이전트 위험 규칙의 경보가 어떤 요구사항의 증거도 아니어서 증거 묶음과 홈 거버넌스 집계에서 빠지던 문제를, 서명·digest로 고정한 대응표 v3로 풀었다. 모든 에이전트 위험 경보가 ISMS-P 2.11.3, AI 기본법 제32조·제34조, EU AI Act 12(2)(a)·14(4)(a)의 검토 자료로 세어지고, 외부 전송·보안 도구 변경·로그 조작은 해당 ISMS-P 항목에도 더해진다.

**배경.** AM-02로 실제 경보가 나오기 시작했지만, 경보는 콘솔 안에서 ‘위험하다’고만 말했다. 오너는 같은 날 아침 어떤 기준으로 감사를 수행하는지 모르겠다고 말한 상태였다. EvidScope에는 이미 AI 기본법·ISMS-P·EU AI Act 증거 묶음과 버전별 대응표(v1, v2)가 있었고, 거버넌스 매핑 모델의 학습 데이터와 어댑터가 v2 대응표의 digest에 묶여 있었다.

**계기.** 오너가 10-15 아침 99% 목표를 말하면서 감사 기준을 모르겠다고 했고, 경보만으로는 ‘그래서 어느 조항과 관련되나’를 답할 수 없었다.

> "사실 어떤 기준으로 감사를 수행하는지 모르겠어."

**문제.** 사용자 규칙 경보는 대응표에 없어서 증거 묶음과 홈의 항목별 증거 수에서 빠졌다. 콘솔은 경보를 보여 줄 뿐 그 경보가 어느 조항을 검토할 때 볼 자료인지 말하지 않았다. 사용자 규칙 코드에는 규칙 버전이 붙어 있어 코드를 정확히 일치시키면 규칙을 고칠 때마다 대응표도 고쳐야 했다.

**당시 제약**

- 대응표는 법 해석이 아니라 사람 검토 전 초안이어야 함(준수 판정 금지)
- 이미 학습한 거버넌스 매핑 어댑터·데이터셋의 digest가 바뀌면 안 됨
- 예전 증거 묶음이 새 검증기에서도 그대로 통과해야 함

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 경보 코드를 버전까지 정확히 일치시켜 대응표에 등록 | 구현이 단순하고 기존 code 필드 그대로 사용 | 규칙을 고쳐 버전이 오를 때마다 대응표를 새로 만들어야 함 |  | 규칙 갱신과 대응표 갱신이 묶이면 운영 부담이 큼 |
| 코드 접두어(codePrefix)로 규칙 묶음이나 규칙의 모든 버전을 함께 지정 | 규칙 버전이 바뀌어도 대응표가 그대로 유효 | 검증기와 집계 코드에 접두어 일치를 새로 넣어야 함 | 선택 | 규칙 운영과 대응표 버전 관리를 분리할 수 있음 |
| 거버넌스 매핑 모델의 카탈로그도 v3로 함께 올림 | 모든 곳이 같은 대응표 버전을 씀 | 학습 데이터와 어댑터의 digest가 바뀌어 기존 학습 결과가 무효가 됨 |  | 카탈로그는 v2에 고정(CATALOG_MAPPING_VERSION) |

**결정.** 증거 묶음 대응표 v3를 만들어 에이전트 위험 규칙 경보를 codePrefix로 요구사항 항목에 연결하고, 3개 프레임워크 파일을 digest로 고정해 검증기 패키지에도 싣는다. 모델 카탈로그는 v2에 둔다. 이유: 경보가 곧 감사 증거 위치가 되게 하면서 규칙 갱신, 기존 묶음, 학습 결과를 모두 깨지 않기 위해서다.

**한 일**

2. 모든 에이전트 위험 규칙을 ISMS-P 2.11.3, KR-32-MONITOR, KR-34-RISK, EU AI Act 12(2)(a)·14(4)(a)에 연결

### AM-05 · 평가 엔진 v5: 여러 행동을 엮는 순서 규칙 5개와 대응표 v4, 실제 미끼 시연

### AM-09 · 지난 행동 가져오기와 엔진 v8

`2026-10-15 → 2026-10-16` · 상태: 완료 · 계기: 오너 피드백 · 결정: AI 에이전트  
*Importing past agent actions from local transcripts and engine v8*

**요약.** hook 설치 전의 AI 행동을 AI 도구가 PC에 남긴 대화 기록에서 읽어, hook이 그때 보냈을 것과 같은 기록으로 소급 수집했다. 도구 이름과 대상만 보내고 내용은 보내지 않았으며, 같은 id를 써서 실시간 기록과 중복되지 않게 했다. Claude Code 78세션의 도구 호출 4,216건에서 6,237건이 새로 저장됐다.

**배경.** AM-02·AM-04로 실시간 수집은 됐지만 hook 설치 전 몇 달간의 AI 행동은 감사 대상이 아니었다. 오너는 같은 시기 콘솔 개편(UX-12)을 요청하면서 지난 행동이 감사되지 않는다는 점도 지적했다. Claude Code와 Codex는 각자 대화 기록 파일을 PC에 남기지만, 그 파일에는 프롬프트·답·도구 출력 등 민감한 내용이 함께 들어 있다.

**계기.** 오너가 실시간 수집 이전의 지난 행동이 감사되지 않는다고 지적했다(콘솔 개편 요청과 함께).

**문제.** hook은 설치 뒤의 도구 호출만 본다. 그 전 행동은 대화 기록 파일에만 있었고, 그 파일을 그대로 넣으면 프롬프트와 파일 내용까지 감사 도구로 들어가 새 유출 경로가 된다. 또 가져온 기록은 원래 늦게 접수되므로 기존 엔진이 기록마다 ‘늦은 증거’ 경보를 내고, 실시간으로 이미 받은 호출과 중복될 수 있었다.

**당시 제약**

- 프롬프트·AI 답·도구 출력·파일 내용·패치 본문은 보내지 않음
- 실시간 hook 기록과 중복되면 안 되고 hook 기록이 우선
- 여러 번 실행해도 안전해야 함
- 약한 증거라는 사실을 숨기지 않음

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 대화 기록 파일 원문을 그대로 수집 | 맥락이 풍부 | 프롬프트·출력·파일 내용이 감사 도구로 들어가 프라이버시와 유출 위험 |  | hook과 같은 최소 정보 원칙 유지 |
| hook이 보냈을 것과 같은 기록(도구 이름·대상·성공 여부)만 같은 id로 전송 | 실시간 기록과 형식·id가 같아 중복이 자동으로 걸러짐, 같은 규칙이 그대로 적용 | 사용자가 고칠 수 있는 파일을 나중에 읽은 것이라 약한 증거 | 선택 | 프라이버시와 중복 방지를 함께 만족 |
| 자산 등록 시점을 과거로 당겨 ‘당시 정책 미확인’ 경보를 없앰 | 경보가 줄어 보기 좋음 | 당시 정책이 없었다는 사실을 숨기는 것 |  | 정직한 공백으로 남기기로 함 |

**결정.** 가져오기 스크립트가 대화 기록에서 도구 호출을 읽어 hook과 같은 기록을 같은 세션·호출 id로 보내고, 기록에 사후 수집 표시를 붙인다. 엔진 v8은 사후 수집 기록에 기록마다 늦은 증거 경보를 내지 않되 늦었다는 사실은 기록에 남긴다. 이유: 과거 행동을 감사 범위에 넣으면서 내용 유출, 중복, 경보 홍수를 피하고 증거 강도를 정직하게 밝히기 위해서다.

**요약.** 위협 10개와 정상 7개 시나리오를 실시간 수집과 같은 형식의 합성 기록으로 만들어 위험 규칙과 순서 규칙에 통과시키고 세션 단위로 채점하는 채점 답안 v1을 만들었다. 규칙만으로 위협 재현율 1.0, 완전 정상 오탐 0, 알려진 과탐 3건이라는 기준선이 생겼고, 이후 보지 않은 유형 210세션에서 위협 120건을 규칙이 모두 잡았지만 설계상 정상인 60세션에도 경보를 냈다.

**배경.** 10-15까지 탐지 성능은 시험 명령 114개와 실제 기록 오탐 수로만 말할 수 있었다. 10-16 오너는 채점 답안, 학습, SIEM 사건화를 한 단계 더 나아가게 하라고 했고 실행은 Opus 에이전트에게 맡겼다. 거버넌스 매핑 모델은 위협 탐지기가 아니었기 때문에, 세션 단위로 위협을 판정하는 새 모델 과제를 정의하려면 먼저 그 모델이 넘어야 할 규칙 기준선이 필요했다.

**계기.** 10-16 오너가 채점 답안·학습·SIEM 사건화를 진전시키라고 요청하고 실행을 에이전트에게 맡겼다. 상세 계획 문서에 데이터 범위·99% 기준·SIEM 범위·학습 시점 네 가지 결정이 걸려 있었다.

**문제.** 규칙이 실제로 위협을 얼마나 잡고 정상 작업에 얼마나 잘못 거는지를 세션 단위 숫자로 말할 수 없었다. 실제 공격 기록은 PC에 없고, 모아도 라벨(정답)에 대한 논쟁이 생긴다. 학습 모델이 규칙보다 나은지 판단할 기준선도 없었다.

**당시 제약**

- 실제 공격 기록 없이 채점해야 함
- 시나리오 기록은 실시간 hook과 같은 형식이어야 같은 규칙을 그대로 통과
- 공격 모양의 명령은 파일 안에만 두고 대화·문서에는 유형과 개수로만 서술
- Store 없이 순수 평가 함수로 돌아야 함(PC 외 환경에서도 실행)

**검토한 대안**

### AM-11 · 경보 처리 원칙: 규칙이 1선, 모델은 2선

`2026-10-17` · 상태: 완료 · 계기: 적대적 감사 · 결정: 오너와 AI 에이전트  
*Alert handling principle: rules first, models second*

**요약.** 적대적 감사에서 학습 모델이 ‘에이전트가 자기 기록 설정을 고친’ 세션 3건을 정상으로 지운 것이 드러나자, 모델은 규칙 경보를 지울 수 없고 우선순위만 낮출 수 있다는 처리 원칙을 코드로 고정했다. 보안 해제·민감 접근 후 외부 전송 같은 연쇄와 읽기가 아닌 기록 변조는 낮추지도 못하는 보호 경보이며, 이후 판정 오케스트라에서는 경보를 낮추려면 두 판정 모델이 모두 동의해야 한다.

**배경.** 10-17 오전 첫 세션 판정 LoRA가 ‘처음 보는 60세션에서 1.0’을 냈지만, 오너가 요청한 적대적 감사에서 이 결과가 누수와 지름길로 설명됐다(JM-12). 같은 감사에서 PC 탐침 시험 중 모델이 자기 설정을 고친 세션을 모두 정상으로 판정했다. 그 뒤 오너는 성능·자원·난이도를 함께 본 ‘최고의 오케스트라’ 계획을 요구했고, 놓치면 안 되는 일은 결정적 코드가, 오탐 정리는 모델이 맡는 구조가 채택됐다.

**계기.** 오너가 학습과 판정의 오류를 최대한 비판적으로 찾으라고 요청한 적대적 감사에서, 학습 모델이 자기 기록 설정을 고친 세션 3건을 정상으로 지웠다.

> "적대적 감사 해보고 학습이랑 판정에서 어떤 오류가 있는지 최대한 비판적으로 제시해봐"

**문제.** 모델 판정을 그대로 최종 결과로 쓰면, 모델이 틀릴 때 확실한 위협 경보까지 사라진다. 실제로 감사 탐침에서 모델은 감사 설정 변조 세션을 정상으로 지웠다. 또 모델이 조항까지 적게 하면 근거 없는 조항이 붙을 수 있었고, 규칙이 못 본 위협을 모델만 찾았을 때 처리 방법도 정해져 있지 않았다.

**당시 제약**

- 확실한 위협은 모델 오류와 무관하게 경보로 남아야 함
- 모델의 가치는 규칙 오탐 감소에 둠
- 조항은 서명된 대응표에서만 계산
- 1인 개발, 12GB GPU 한 대에서 돌릴 수 있는 구조

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 모델 판정을 최종 결과로 사용(정상이면 경보 삭제) | 오탐이 가장 크게 줄어듦 | 모델이 틀리면 확실한 위협도 사라짐, 감사에서 실제로 발생 |  | 놓치면 안 되는 것을 확률 모델에 맡길 수 없음 |
| 모델은 경보를 지우지 못하고 우선순위만 낮춤, 일부 경보는 보호 | 위협 누락을 구조적으로 막고 모델은 오탐 정리에만 기여 | 보호 경보에 속한 정상 세션은 계속 경보로 남음 | 선택 | 탐지 책임은 결정적 코드에 두기로 함 |
| 판정 모델 하나의 의견으로 경보를 낮춤 | 호출 비용이 적음 | 한 모델의 오판이 그대로 반영 |  | 오케스트라에서는 두 판정 모델이 모두 동의해야 낮춤 |

**결정.** src/session-disposition.mjs: 모델은 경보를 low로만 낮출 수 있고, 보안 기능 해제, 민감 접근 후 외부 전송, 보안 해제 후 행동, 읽기가 아닌 기록 변조와 위험 후 변조 연쇄는 보호 경보로 낮출 수 없다. 규칙이 못 본 세션을 모델이 위반이라 하면 사람 검토 항목이 된다. src/judge-orchestra.mjs: 첫 판정 모델이 모든 세션을 보고, 두 번째 모델은 필요할 때만 부르며, 낮추려면 둘 다 동의해야 한다. 조항은 대응표에서 계산한다. 이유: 놓치면 안 되는 것은 결정적 코드(규칙·순서·내용 검사·대응표)가 맡고 모델은 오탐 감소에만 쓰기 위해서다.

**한 일**

1. src/session-disposition.mjs(51줄): 처리 함수와 보호 경보 판정, 읽기 행동의 설정 접근은 낮출 수 있게 구분

### AM-12 · 평가 엔진 v9: LLM 보안 신호, 작업 범위, 에이전트 간섭 규칙(규칙 67개), 대응표 v5

`2026-10-17` · 상태: 완료 · 계기: 계획 · 결정: AI 에이전트  
*Evaluation engine v9: LLM security signals, agent scope and interference rules (67 rules), mapping v5*

**요약.** hook이 AI가 읽는 글(도구 결과, 선택적으로 사용자 프롬프트)을 메모리에서 검사해 신호의 종류·개수·글자 수·해시만 보내게 하고, 엔진 v9가 이를 간접 주입·비밀/개인정보 전송·‘주입 문구 뒤 위험 행동’ 연쇄 같은 발견사항으로 바꾸게 했다. 실행 전 기록에 권한 모드·샌드박스·작업 폴더 밖 접근을 붙였고, 다른 에이전트 간섭 4개와 EvidScope 수집 중단 3개 규칙을 더해 규칙이 67개가 됐다.

**배경.** 10-17 기준 남은 공백은 프롬프트 주입·탈옥·목표 탈취, 결과 속 민감 데이터, 다른 에이전트 간섭, EvidScope 기록 삭제·수집 중단이었다. hook은 도구 호출의 대상만 보고 프롬프트나 도구 결과는 보지 않았다. 오너가 고른 오케스트라 계획의 작업 순서가 ‘엔진 v9와 새 규칙, 작업 범위 기록, 차단 기능, 그다음 PC 반영’이었다. 같은 날 오너는 최종 목표가 PC가 아니라 회사 내부망 감사라고 밝혔고, 에이전트의 작업 폴더·권한·샌드박스 모드는 그 목표에서 빠진 항목으로 꼽혀 있었다.

**계기.** 오케스트라 계획의 구현 순서 첫 단계였고, 오너가 밝힌 회사 내부망 감사 목표에서 빠진 항목(에이전트 작업 범위 기록)과 남은 공백 목록이 함께 근거가 됐다.

> "PC 뿐만이 아니라 내부망, 즉 회사나 내부 vpc 내에서 감사를 하는 게 목적"

**문제.** 웹 페이지·파일·MCP 응답에 숨은 지시가 에이전트를 움직여도 EvidScope는 알 수 없었다. 비밀 값이나 개인정보가 AI 서비스로 넘어가는 것도 보이지 않았다. 다른 AI 에이전트의 전역 지시 파일·MCP 설정을 바꾸거나 다른 에이전트 프로세스를 끄는 행동, EvidScope 수집을 멈추는 행동에 대한 규칙이 없었다. 에이전트가 승인 확인을 끈 모드에서 일했는지, 작업 폴더 밖을 고쳤는지도 기록에 없었다.

**당시 제약**

- 모델 없이 결정적으로 동작해야 하고 재생 호환을 지켜야 함
- 프로젝트 안의 정상 작업(지시 파일 수정, 프로세스 조회, 개발 서버 종료)은 걸리면 안 됨

### AM-13 · 실행 전 차단: 확실한 것만 차단

`2026-10-17` · 상태: 완료 · 계기: 오너 요청 · 결정: 오너  
*Pre-execution blocking: block only the certain cases*

**요약.** 오너가 ‘확실한 것만 차단’을 골라, Claude Code의 실행 전 hook이 감사·수집 설정 조작, 보안 기능 끄기, 비밀을 읽어 바로 외부로 보내는 한 명령만 실제로 막게 했다. 막을 때는 한국어 이유가 담긴 거부 응답을 내고 그 호출은 ‘차단됨’ 표시와 함께 원장에 남으며, 나머지는 지금처럼 경보만 낸다.

**배경.** AM-02부터 hook은 절대 막지 않는 원칙으로 동작했고, 모든 탐지는 일이 일어난 뒤의 경보였다. 오케스트라 계획을 정하던 10-17 오전, 차단 수준을 묻는 카드가 함께 올라갔다. EvidScope는 원래 차단은 집행 지점이 하고 자신은 증거만 남긴다는 설계였지만, 에이전트가 감사 도구 자체를 끄는 행동은 사후 경보로는 늦다. Codex는 거부 응답 형식을 PC에서 확인하지 못한 상태였다.

**계기.** 차단 수준 카드에서 오너가 세 선택지 중 ‘확실한 것만 차단’을 골랐다.

> "확실한 것만 차단"

**문제.** 경보만으로는 이미 일어난 뒤에 안다. 특히 에이전트가 EvidScope 수집 설정이나 hook을 고치면 그 뒤의 기록이 사라질 수 있다. 반대로 차단이 넓으면 정상 개발 작업이 멈춘다. 설정 파일을 읽기만 하는 것과 고치는 것을 구분하지 않으면 일상 작업까지 막힌다.

**당시 제약**

- 오차단은 개발을 멈추므로 맥락과 무관하게 문제인 것만 막음
- 막은 사실도 원장에 남아야 함
- 규칙 팩을 읽지 못해도 작업을 멈추지 않아야 함
- Codex 거부 응답 형식은 미확인

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 확실한 것만 차단 | 감사 도구 무력화와 명백한 유출을 실행 전에 막으면서 오차단을 최소화 | 그 밖의 위험 행동은 여전히 사후 경보 | 선택 | 오너 선택(추천안) |
| 경보만 | 작업 방해 위험 0 | 감사 설정 변조처럼 사후에는 늦는 행동도 막지 못함 |  | 오너가 고르지 않음 |
| 고위험 전부 차단 | 가장 강한 보호 | 정상 개발 중 걸리는 high 규칙(예: 자기 브랜치 강제 푸시)까지 막아 개발이 멈춤 |  | 오너가 고르지 않음 |
| 규칙 팩을 못 읽으면 모두 막기(fail-closed) | 우회 여지가 적음 | 설치 오류 하나로 AI 작업 전체가 멈춤 |  | 작업을 멈추지 않는 fail-open을 택하고 그 사실을 로그에 남김 |

**결정.** Claude Code의 실행 전 hook만 차단한다. 대상은 감사·수집 설정 조작(EvidScope hook 설정, AI 도구의 hook 설정 변경, EvidScope 예약 작업·프로세스 중지, 설치된 hook 변경), 보안 기능 끄기, 비밀 읽기와 외부 전송이 한 명령에 함께 걸리는 경우다. 설정 파일 읽기와 보여 주기만 하는 셸 명령은 통과시키되 EvidScope hook 설정은 수집 자격이 있어 읽기도 막는다. Codex는 경보만 낸다. 이유: 오차단으로 개발을 멈추지 않으면서 감사 도구 무력화와 명백한 비밀 유출만 실행 전에 막기 위해서다.

**한 일**

1. src/agent-hook-guard.mjs(62줄): 실행 전 기록을 규칙 팩과 맞춰 차단 대상 규칙 12종과 ‘비밀+외부 전송’ 조합만 거부

<a id="am-14"></a>
### AM-14 · 에이전트 자동 등록과 책임자 연결

`2026-10-18` · 상태: 완료 · 계기: 오너 피드백 · 결정: 오너와 AI 에이전트  
*Agent auto-registration and accountable-owner mapping*

**요약.** 오너가 ‘이 에이전트가 누구 것이고 누가 책임지는지 판정하는 기능이 없다’고 지적해, hook이 실행자(OS 계정·PC·git 저장소·git 사용자)를 기록마다 싣고, 새로 보인 에이전트를 책임자 없는 ‘발견됨’ 항목으로 자동 등록하며, 매핑 표로 팀·책임자를 추정하고, 검토자가 확정해야만 ‘확정’이 되게 했다. 경보와 증거 묶음에도 에이전트·실행자·책임자를 함께 보여 준다.

**배경.** 서명된 에이전트 레지스트리(등록·생애주기·4-eyes)와 미등록 후보 목록, Backstage·A2A 카탈로그 가져오기는 이미 있었다. 하지만 후보는 보여 주기만 하고 사람이 손으로 등록해야 했고, hook 기록에는 ‘에이전트@PC이름’뿐이라 어느 계정·저장소·팀의 작업인지 알 수 없었다. 경보와 증거 묶음에도 책임자가 없었다. 목표 배포는 회사 내부망이라, 여러 사람·여러 PC의 에이전트를 팀과 책임자에 연결해야 감사 서비스로 쓸 수 있다.

**계기.** 판정 테스트 화면을 보던 중 오너가 소유자·책임 판정과 자동 등록이 없다는 점을 지적했다.

> "누구 소유 에이전트인지 어떤 이어 책임 소유인지 판정하기 아직 없지 않냐? 에이전트들 자동 등록 기능이랑 소유자 매핑 같은거"

**문제.** 책임 소재를 시스템이 정하면 안 된다. 실행자 정보는 에이전트 자신의 보고라 틀릴 수 있고, 자동 등록한 항목이 행위자를 포함하면 ‘미등록 활동’ 경고가 사람 검토 없이 사라진다. 또 기존 평가 결과와 재계산(재생), 예전 증거 묶음의 검증이 그대로 통과해야 했다.

**당시 제약**

- 책임자 확정은 사람만
- 자동 등록이 발견(finding)과 평가 재생 결과를 바꾸면 안 됨
- 예전 EvidScope 서버와 예전 증거 묶음과 호환
- hook은 도구 호출마다 실행되므로 git 프로세스를 띄우지 않음
- 공개 저장소: 실명·경로·비밀 없음

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 자동 등록 항목에 행위자·출처를 채워 바로 활동을 포함 | 등록 즉시 경보·생애주기와 연결됨 | 사람 검토 없이 미등록 활동 경고가 사라지고 평가 엔진 결과가 바뀜 |  | 책임 판단을 시스템이 대신하게 됨 |
| 자동 등록은 빈 ‘발견됨’ 항목, 책임자는 추정·확정 2단계 | 발견을 바꾸지 않고 재생 결과도 같음, 추정 근거(규칙·값·표 버전)를 보여 줌 | 검토자가 확정하고 행위자를 넣는 일이 남음 | 선택 | 메인 스레드 제안(발견됨→추정→확정)을 따르되, 자동 항목이 활동을 포함하지 않게 해 엔진 버전을 올리지 않음 |
| 추정 책임자를 owner 필드에 바로 기록 | 구현이 단순 | 승인 게이트의 책임자 조건이 추정만으로 통과됨 |  | 추정과 확정을 구분하지 못함 |
| 실행자를 데이터 범주 꼬리표로 싣기 | 수집 계약을 바꾸지 않음 | 64자 제한, 위험 규칙 입력과 섞임 |  | 전용 executor 필드를 두고, 예전 서버가 거부하면 hook이 필드를 빼고 다시 보냄 |

**결정.** hook이 기록마다 executor(OS 계정·PC·origin 저장소·git 사용자)를 싣는다. 레지스트리 정책 autoRegister를 켜면 1분마다 새 후보를 책임자·출처·행위자·구성이 빈 ‘발견됨’ 항목으로 등록한다. 관리자가 정한 매핑 표(계정·PC·저장소·git 사용자·행위자·출처 → 팀·책임자, 순서가 우선순위)로 책임자를 추정하고, 서로 다른 책임자가 나오면 ‘충돌’로 둔다. 검토자가 사유와 함께 확정해야 ‘확정’이 되고, 승인 게이트는 확정된 책임자만 인정한다. 경보 API·콘솔 경보 표·증거 묶음 accountability.json에 함께 싣는다. 이유: 누구의 에이전트인지 근거와 함께 보여 주되, 책임 확정은 사람의 서명 기록으로만 남기기 위해서다.

**한 일**

1. src/agent-ownership.mjs(156줄): 실행자 읽기, 매핑 규칙 일치, 추정·충돌·확정 상태, 기록별 책임 정보, 내보내기의 책임 보고서
2. hook: .git/config·~/.gitconfig 파일만 읽어 저장소(주소 속 사용자·토큰 제거)와 git 사용자 확인, 설정 executor:false로 끔, 예전 서버가 거부하면 필드 없이 재전송
3. 수집 계약: executor 필드는 agent 출처만, 알려진 네 필드만 허용
4. 레지스트리: autoRegister 정책, POST /api/registry/discover(미리보기), 매핑 표 GET·POST /api/registry/owners(관리자), POST /api/registry/:id/owner(사유 필수), 목록·상세·후보에 실행자와 책임자 상태
5. 서명 이력 검증: 자동 등록 항목이 빈 발견됨으로 시작했는지, 책임자 확정이 확정한 검토자 서명인지 확인

7. 증거 묶음: accountability.json을 넣고 검증기가 내보내기에서 다시 만들어 바이트 대조, 예전 묶음은 그대로 통과

**결과.** 컨테이너 시험에서 에이전트 두 개가 보이면 자동 등록이 둘 다 ‘발견됨’으로 등록하고(다시 돌려도 중복 없음), 저장소 규칙에 맞는 쪽은 ‘추정 pay-lead(payments)’, 맞지 않는 쪽은 ‘미확인’으로 나왔다. 추정만으로는 승인 게이트의 책임자 조건이 충족되지 않았고, 검토자가 확정하자 ‘확정’과 확정자·근거가 새 버전에 남았다. 해당 에이전트의 경보에 계정·책임자가 함께 붙었고, 내보내기의 서명 이력 검증과 책임 보고서 재생성이 통과했다. PC에는 아직 적용하지 않았다.

### AM-15 · 수집 연속성: hook 기록의 순번·연결과 빠짐 경보

`2026-10-18` · 상태: 완료 · 계기: 오너 피드백 · 결정: 오너와 AI 에이전트  
*Collection continuity: numbered, linked hook records and gap alerts*

**요약.** 오너가 ‘모든 LLM 활동 로그를 무결하게 수집하는 것’이 핵심이라고 해, hook이 기록마다 순번과 앞 기록의 지문을 붙이고, 금고가 빠진 순번·앞 기록과 맞지 않는 연결·중복 번호를 찾아 서명된 수집 공백 기록과 높음 경보로 남기게 했다.

**배경.** 서명 원장은 기록이 EvidScope에 도착한 뒤의 삭제·변경을 드러내지만, PC의 hook에서 금고까지 오는 사이에 기록이 빠지거나 바뀌어도 알 방법이 없었다. 대기 파일(spool)이 가득 차거나 4xx로 버려진 기록, 누가 대기 파일 줄을 지운 경우가 모두 조용히 사라졌다.

**계기.** 책임자 연결 작업 직후 오너가 수집 무결성을 핵심 요구로 짚었고, 결정 카드에서 ‘빠짐 감지’를 먼저 만들기로 골랐다.

> "사실 중요한 것 중 하나는 모든 llm활동의 로그를 무결하게 수집하는거야"

**문제.** hook은 도구 호출마다 따로 실행되는 짧은 프로세스라 여러 개가 동시에 돌고, 금고가 꺼져 있으면 기록이 나중에 순서가 바뀐 채 도착한다. 이 상태에서 빠짐과 변경을 오탐 없이 가려야 했고, 평가 엔진·예전 서버·예전 증거 묶음은 그대로여야 했다.

**당시 제약**

- hook은 node 기본 모듈만 사용
- 평가 엔진 버전을 올리지 않음
- 예전 EvidScope가 새 필드를 거부하면 hook이 필드 없이 다시 보냄
- 대기 파일 기록은 늦게 도착할 수 있음
- 공개 저장소: 실명·경로·비밀 없음

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 기록마다 순번과 앞 기록 지문(해시 사슬) | 빠짐·변경·중복을 각각 구분, 금고가 이미 저장하는 원문 지문과 바로 대조 | 상태 파일과 잠금이 필요, 끝부분 삭제는 못 봄 | 선택 | 서버가 이미 가진 지문 비교(compareEventFingerprint)를 그대로 쓰고 엔진을 바꾸지 않음 |
| 대기 파일에 HMAC 서명 | 대기 파일 변조를 바로 감지 | 서명 키가 hook 설정과 같은 곳에 있어 설정을 읽을 수 있는 사람은 다시 서명 가능 |  | 보호 효과가 순번 사슬보다 작고, 지워진 줄은 어차피 순번 빈 곳으로 드러남 |
| 주기적 심장박동(heartbeat)으로 끝부분 삭제까지 감지 | 마지막 기록 이후 삭제도 드러남 | hook은 상주 프로세스가 아니라 별도 발신기가 필요 |  | 다음 단계로 남김(결정 카드의 다른 선택지) |

**결정.** hook이 ~/.evidscope/<에이전트>-chain.json 상태와 잠금 파일로 기록마다 chain {stream, seq, prev}를 붙인다. 금고는 출처·스트림별로 순번을 모아 빠진 구간(뒤 순번 도착 1시간 뒤 확정), 연결 불일치, 번호 중복, 재시작을 보고하고, 5분마다 새 문제를 서명된 telemetry gap 기록으로 한 번씩 남겨 기존 COLLECTION_GAP 경보가 되게 한다. 이유: 원장이 지키는 ‘도착 이후’에 더해 ‘도착 이전’ 구간의 유실·변경을 근거와 함께 보이기 위해서다.

**한 일**

1. hook: 정규 JSON 지문 계산(서버와 같은 sha256), 잠금 파일로 동시 프로세스 순번 보장, 상태 파일 원자적 교체, 설정 chain:false로 끔
2. 수집 계약: chain 필드는 agent 출처만, 정확한 모양만 허용
3. src/collection-chain.mjs: 스트림별 빠진 구간(도착 대기·확정)·연결 불일치·번호 중복·재시작·순번 없는 기록 집계와 문제 목록

### AM-16 · 로컬 모델 기록 프록시: Ollama·vLLM 호출을 서명 사슬에 남기기

`2026-10-18` · 상태: 완료 · 계기: 오너 피드백 · 결정: AI 에이전트  
*Recording proxy for local model servers: Ollama and vLLM calls in the signed chain*

**요약.** 오너가 유명 로컬 모델에도 적용할 수 있어야 한다고 해, Ollama·vLLM·LM Studio 같은 OpenAI 호환 모델 서버 앞에 두는 기록 프록시를 만들었다. 어떤 도구가 부르든 모델 호출마다 요청·내용 검사·응답 기록을 본문 없이 서명·순번 사슬로 남기고, 상주 프로세스의 심장박동으로 hook이 못 보던 끝부분 삭제까지 드러나게 했다.

**배경.** 수집은 Claude Code·Codex hook뿐이었다. 로컬 모델을 부르는 Open WebUI, Continue, Aider, 직접 짠 스크립트에는 hook이 없어 사내에서 로컬 모델을 써도 EvidScope에는 아무 기록이 남지 않았다.

**계기.** 학습 스레드에서 판정 모델 평가를 이야기하던 중 오너가 로컬 모델 적용을 짚었고, 판정 쪽(로컬 모델 비교)은 학습 스레드가, 수집 쪽은 별도 스레드가 맡았다.

> "적어도 네임드 모델들을 상대로 좋은 평가 내는 것도 중요하지만, 유명 로컬 모델들에도 적용할 수 있어야겠지"

**문제.** 도구마다 확장 지점이 달라 도구별 연동은 끝이 없다. 모델 호출을 빠짐없이, 사용을 방해하지 않고(스트리밍 유지, 기록 실패가 호출을 막지 않음), 본문을 원장에 넣지 않으면서 기록해야 했다.

**당시 제약**

- 응답은 바이트 그대로, 받는 즉시 전달
- 본문은 기본으로 저장하지 않음
- 기존 hook 기록 형식·순번 사슬·서명 요청을 그대로 사용
- 평가 엔진 버전을 올리지 않음
- PC에 서비스·자동 시작·시스템 프록시를 등록하지 않음

**검토한 대안**

| 대안 | 장점 | 단점 | 선택 | 이유 |
|---|---|---|---|---|
| 모델 서버 앞 HTTP 기록 프록시 | OpenAI 호환 API와 Ollama API만 알면 어떤 도구든 기록, 상주 프로세스라 심장박동 가능 | 도구가 서버를 직접 부르면 빠짐(망 설정으로 막아야 함) | 선택 | 로컬 모델 도구 대부분이 같은 두 API를 쓰므로 한 곳에서 모두 덮음 |
| 도구별 플러그인·hook(Open WebUI 함수, Continue 확장 등) | 도구 안의 맥락(사용자, 화면)을 더 볼 수 있음 | 도구마다 따로 만들고 버전마다 깨짐, hook이 없는 도구는 불가 |  | 덮는 범위가 좁고 유지 비용이 큼 |
| 패킷 관측(Zeek 등) | 도구 협조 없이 관측 | 로컬 루프백 트래픽과 본문 의미(모델·토큰·도구 호출)를 보기 어려움 |  | 모델 호출 단위 기록이 안 됨 |

**결정.** scripts/local-model-proxy.mjs init/run과 src/local-model-proxy.mjs. 모델 엔드포인트(/v1/chat/completions, /v1/responses, /api/chat 등)를 지나는 호출마다 intent(모델·메시지 수·건넨 도구 이름·요청 SHA-256), 새 메시지와 도구 결과의 내용 검사 기록, self_report(HTTP 상태·종료 이유·모델이 부르려 한 도구 이름·토큰 수·응답 SHA-256·aiObservation)를 순번 사슬로 보낸다. 본문 보관은 선택(기본 꺼짐)이며 보관 본문의 해시가 서명 기록의 해시와 같다. 이유: 모든 LLM 활동을 무결하게 수집한다는 목표를 hook이 없는 로컬 모델 도구까지 넓히기 위해서다.

**한 일**

1. SSE(OpenAI 호환)·NDJSON(Ollama)·JSON 응답을 흘려보내며 옆에서 읽는 응답 탭(여러 바이트 글자가 조각 사이에 잘려도 정상)
2. 대화 API가 매번 보내는 전체 대화 중 모델의 마지막 답 뒤 새 메시지만 검사해 반복 경보 방지
3. content-rules가 프록시의 내용 검사 기록도 읽게 해 LLM_SECRET_IN_PROMPT 등 v9 발견이 로컬 모델에도 나옴
4. 시작·10분마다 순번 붙은 심장박동 기록, EvidScope가 꺼지면 순서대로 대기 파일에 보관 후 재전송
5. init이 기존 hook 설정의 자격 증명을 복사하고, --local-dir로 프록시를 자산 등록
6. test/local-model-proxy.test.mjs: 가짜 모델 서버·가짜 수집기로 통과·서명·순번·대기·심장박동·본문 보관, 금고까지 끝까지

**결과.** 컨테이너 시험에서 가짜 OpenAI 호환 서버의 스트리밍 응답과 가짜 Ollama 응답이 프록시를 지나 바이트 그대로 도착했고, 호출마다 서명된 기록이 1번부터 빈틈없이 이어졌다. 기록 어디에도 프롬프트·응답 글·API 키가 없었다. 금고까지 끝까지 시험에서 로컬 모델에 가짜 클라우드 키를 붙여 넣은 호출이 높음 LLM_SECRET_IN_PROMPT 경보가 됐고, 등록된 프록시에는 미등록 경보가 없었다. 실제 Ollama·vLLM과 PC에서는 아직 실행하지 않았다.
