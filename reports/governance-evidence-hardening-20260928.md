기존 전체 회귀 통과 이후, 평가 생성과 금융 증빙 조회에서 추가로 변조 경로를 재현했다. 조회용 SQL 사본을 변조한 공격자는 정상 서명된 자료와 다른 내용을 새 평가·보고서에 연결할 수 있었다. 서명이 원래 출처의 진실성을 보증하지 않는다는 한계와 별개로, 저장된 서명 원본과 현재 조회 자료의 일치를 보장해야 하는 구현 결함이다.

**최종 전체 회귀 425/425 통과(실패·skip 0, 74.2초)**: [전체 로그](governance-hardening-tests-20260928.log). 수정 이미지의 Linux 금융·복구 회귀도 **39/39 통과(2.1초)**: [컨테이너 로그](governance-container-tests-20260928.log). 이미지 `evidscope:enterprise-20260928-r2`, manifest list digest `sha256:12bc307d53b68987c268ced6981385b8dd0667de5368a7ce011614410bfb9178`. 외부 네트워크 차단, 비관리자, 읽기 전용 rootfs, CPU2·RAM1GiB의 임시 컨테이너로 검증하고 자동 제거했다. 운영 배포는 하지 않았다.

## 평가와 보고서

- 시스템 ID·본문·누락·추가 사본을 서명 원장과 대조한 뒤 같은 트랜잭션에서 평가를 저장한다.
- 이벤트 참조는 같은 테넌트의 보존 중인 서명 원본에서 찾고 조회 사본과 대조한다. 사용자가 적은 이벤트 해시 대신 실제 참조 원본의 해시를 고정한다.
- 일반 거버넌스 보고서도 시스템·평가·담당 과제를 검증하고, 새 형식의 이벤트 참조는 내용 해시를 확인한다. 정당한 보존 종료로 사라진 근거는 재검토 대상으로 남긴다.
- 외부 문서 URL이나 사용자 해시는 실제 파일 조회로 표시하지 않는다. 공급사 파일 검증과 외부 참조의 차이를 유지한다.

신규 평가·보고서 회귀 9건은 수정 전 모두 실패했다. 이 중 시스템 ID 변경·삭제는 기존 404 대신 무결성 충돌을 확인하는 회귀이며, 나머지는 잘못된 내용 수용을 직접 재현한다. 수정 후 기존 금융 사례와 합쳐 21/21을 통과했다. 실제 HTTP·한국법 적용 후보·기존 통합 20/20도 통과했다.

## 공급사 묶음의 식별자

금융 검증이 사본의 본문 목록만 비교하던 문제를 수정했다. SQL ID와 서명 객체 ID를 함께 검사하여 서로 다른 시스템·묶음의 이름을 바꾸거나 교환한 경우 내보내기·보고서를 409로 거부한다. 신규 4개 공격 경로가 수정 전 재현됐고 수정 후 기존 금융 사례와 합쳐 17/17을 통과했다. 다른 테넌트의 문서 바이트를 반환하지 않는 것도 확인했다.

추가 독립 검토로 검증 직후 SQL 사본이 바뀌는 시간차 결함을 찾았다. 금융 조회·내보내기·가져오기·보고서 저장은 이제 검증부터 조회·서명까지 같은 `BEGIN IMMEDIATE` 트랜잭션을 유지한다. 내부 호출은 고유 SAVEPOINT를 사용하며 외부 작업을 조기 커밋하지 않는다. 별도 실제 SQLite 연결에서 검증 직후 변조하는 5개 경로는 수정 전 모두 성공했고, 수정 후 모두 `SQLITE_BUSY`로 차단됐다. 내부 실패의 부분 rollback과 외부 실패의 전체 rollback에서도 원장·체크포인트·객체가 일치하는지 확인했다. 관련 새 회귀 9/9 통과. 긴 금융 보고서가 같은 SQLite의 쓰기를 기다리게 할 수 있으므로 대용량 운영 부하 검증은 여전히 필요하다.

공식 KLUE dev의 고정 원본에서 답변 가능 32개·불가 32개를 준비했다. 학습·검증 데이터와 ID·문서 해시·family 중복이 없으며 전체 원문과 사람이 작성한 원래 정답 위치를 보존했다. 정답을 보고 문맥을 자르지 않는다. 코드의 개인정보 패턴 검사는 완전한 개인정보 검토가 아니다.
